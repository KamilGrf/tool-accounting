## 1. Архитектура и выбор решения

```
┌──────────────────────┐   supabase-js (HTTPS)   ┌─────────────────────────────────────────────┐
│ Браузер: React SPA   │ ──────────────────────► │ Supabase                                    │
│ (статика на Vercel)  │ ◄────────────────────── │  Auth      — вход, токен (JWT)              │
└──────────────────────┘                         │  PostgREST — REST поверх таблиц и функций   │
                                                 │  PostgreSQL — схема, RLS, функции, триггеры │
                                                 └─────────────────────────────────────────────┘
```

Собственного сервера нет. Всё, что раньше делал Node.js API (проверка прав, транзакции выдачи и возврата, отчёты), теперь в базе данных.

**Выбор: вариант A (Supabase).** Предыдущая версия — вариант B: PostgreSQL в Docker и собственный API на Node.js.

| Критерий | Supabase (выбран) | Self-hosted (предыдущая версия) |
|---|---|---|
| Хостинг | Только статика (Vercel) плюс облако Supabase; сервер не нужен | Нужен хостинг для Docker/Node и базы; бесплатные варианты часто требуют карту |
| Вход и пароли | Готовый Supabase Auth | Собственные scrypt и JWT-cookie, блокировка входов |
| Права | RLS и функции прямо в базе | Проверка в коде маршрутов |
| Бизнес-логика | SQL-функции (plpgsql) | Обычный код на JavaScript |
| Минусы | Логика на SQL, привязка к платформе, лимиты бесплатного тарифа, часть защиты (блокировка входов) стала слабее | Больше кода и ответственности, нужен хостинг |

Причина выбора: публичная ссылка на работающую систему без отдельного сервера. Цена: см. раздел 9 (что стало слабее).

## 2. База данных

### 2.1. Схема

```
auth.users 1──1 profiles (role: storekeeper | manager)
categories 1──* tools 1──* issues *──1 employees
                           issued_by, returned_by ──► profiles
```

| Таблица | Назначение и главные ограничения |
|---|---|
| `profiles` | Роль и email пользователя. Создаётся триггером при регистрации, роль всегда `storekeeper` |
| `categories` | Название уникально, 1–80 символов |
| `tools` | Инвентарный номер уникален без учёта регистра, цена ≥ 0, статус из четырёх значений, длины полей ограничены (`CHECK`) |
| `employees` | ФИО 1–120, остальное короче |
| `issues` | Срок ≥ даты выдачи; **частичный уникальный индекс**: у инструмента не может быть двух незакрытых выдач (защита от гонки на уровне БД) |

Миграции — в `supabase/migrations/` (применять по номерам): `001` схема, `002` профили и вспомогательные функции, `003` RLS и права, `004` представления, защита статусов, функции и отчёты.

Отличия от предыдущей версии: пользователи в `auth.users` + `profiles` (вместо таблицы `users` с хэшами), «кто выдал» — uuid и снимок email (`issued_by_login`), ограничения длины полей вынесены из кода в `CHECK`, «сегодня» считается по московскому времени функцией `today_local()`.

### 2.2. Представления и функции

| Объект | Кто | Что делает |
|---|---|---|
| `v_tools`, `v_issues`, `v_employees`, `v_categories` | сотрудники | Выборки с названием категории, флагом просрочки, числом активных выдач. `security_invoker`: права вызывающего сохраняются |
| `list_tools(q, category, status)` | сотрудники | Поиск без учёта регистра, `%` и `_` ищутся буквально, неизвестный статус даёт ошибку |
| `list_issues(active, overdue, employee, tool)`, `list_employees(q)` | сотрудники | Списки с фильтрами |
| `issue_tool`, `return_tool`, `extend_issue` | сотрудники | Выдача, возврат (в ремонт или на склад), продление срока; блокировка строки `FOR UPDATE`, те же сообщения об ошибках, что в предыдущей версии |
| `report_stats()`, `report_usage(category)` | **руководитель** | Сводка и отчёт об использовании |
| Триггер `tools_guard_update` | — | Статус «Выдан» меняется только функциями выдачи и возврата; списание и возврат из списания — только руководитель |

## 3. Развёртывание

Пошаговая инструкция — в [README.md](README.md). Кратко: проект Supabase → выполнить миграции и `seed.sql` в SQL Editor → настроить вход по email → назначить руководителя SQL-командой → указать `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` → собрать frontend (Vercel, Root Directory `frontend`).

Секреты: в браузер попадает только публичный `anon`-ключ. Ключ `service_role` и пароль базы нигде в репозитории и в приложении не используются; `.env` исключён из git.

## 4. API

Клиент (`frontend/src/api/index.js`) вызывает Supabase; под капотом это REST PostgREST. Для проверки без приложения нужен токен пользователя:

```bash
# 1) токен (Supabase Auth); значения возьмите из Project Settings -> API
curl -s -X POST "$SUPABASE_URL/auth/v1/token?grant_type=password" \
  -H "apikey: $ANON_KEY" -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"..."}'
# 2) запрос с токеном
curl -s -X POST "$SUPABASE_URL/rest/v1/rpc/list_tools" \
  -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d '{"p_q":"bosch"}'
```

| Операция в приложении | Вызов | Доступ |
|---|---|---|
| Список инструментов | `rpc/list_tools` | сотрудник |
| Добавить / изменить инструмент | `POST/PATCH /rest/v1/tools` | сотрудник (списание — руководитель) |
| Удалить инструмент | `DELETE /rest/v1/tools` (в интерфейсе нет) | руководитель, и только без истории выдач |
| Категории | `GET /rest/v1/v_categories` | сотрудник |
| Сотрудники | `rpc/list_employees` | сотрудник |
| Выдачи | `rpc/list_issues` | сотрудник |
| Выдать / принять / продлить | `rpc/issue_tool`, `rpc/return_tool`, `rpc/extend_issue` | сотрудник |
| Сводка, использование | `rpc/report_stats`, `rpc/report_usage` | руководитель |
| Вход, регистрация, выход | Supabase Auth | все |
| CSV просрочек | собирается в браузере из `list_issues` | руководитель (кнопка на странице отчёта) |

**Права на таблицы (RLS):** анонимный пользователь не видит ничего; сотрудник читает все таблицы и пишет в `categories`, `employees`, `tools`; в `issues` клиент не пишет вообще (только через функции); `profiles` читается только своя строка и не изменяется клиентом; удалять инструменты может только руководитель.

## 5. Безопасность

| Мера | Как сделано |
|---|---|
| Доступ по умолчанию закрыт | RLS включён на всех таблицах, у `anon` отсутствуют права на таблицы, представления и функции |
| Роль нельзя подделать | Хранится в `profiles`; триггер создаёт только `storekeeper`; клиент не может изменить `profiles` (тест `a storekeeper cannot promote himself`) |
| Внутренние функции | Функции-«обёртки» (`security definer`) работают с `search_path = ''` и сами проверяют роль |
| Внутренний флаг статуса | Устанавливается только внутри функций выдачи и возврата; клиент не может выставить его |
| Данные проверяются в БД | Ограничения `CHECK`, уникальные индексы, проверки внутри функций; клиентские проверки лишь удобство |
| LIKE-спецсимволы | `%` и `_` в поиске экранируются |
| Секреты | В браузере только `anon`-ключ; `.env` не коммитится |
| Токен сессии | Supabase хранит его в `localStorage` браузера: при XSS его можно украсть. Защита: интерфейс не вставляет данные в HTML (`dangerouslySetInnerHTML` запрещён правилами), всё выводится через JSX |

**CORS:** насколько мне известно, публичный API Supabase принимает запросы с любых источников (не проверял), поэтому ограничением служат токены и RLS, а не адрес сайта. Список адресов в настройках Auth нужен для ссылок из писем и перенаправлений.

## 6. Обработка ошибок и журналы

База поднимает ошибки с кодами `P0400` (неверные данные), `P0401` (нет входа), `P0403` (нет прав), `P0404` (не найдено), `P0409` (конфликт) и русским текстом, который показывается пользователю как есть. Остальное переводит `frontend/src/api/client.js`:

| Ситуация | Что видит пользователь |
|---|---|
| Нет соединения или таймаут 15 с | «Не удалось связаться с сервером. Проверьте соединение» (+ «Повторить») |
| Нарушение уникальности | Сообщение по конкретному ограничению (например, номер уже занят) |
| `CHECK`, неверный тип | «Некорректные данные в запросе» |
| Нет прав (RLS) | «Недостаточно прав» |
| Просроченный токен | Возврат на экран входа с сообщением «Сессия истекла» |
| Прочее | «Внутренняя ошибка сервера. Попробуйте позже», подробности наружу не попадают |

**Журналы:** собственного журнала нет. Запросы и ошибки смотрите в Supabase (раздел Logs); я его не открывал и содержимое не проверял.

## 7. Тестирование

| Набор | Команда | Что проверяет | Результат |
|---|---|---|---|
| Интерфейс и слой доступа | `npm test` в `frontend` | Страницы, роли, вход, разбор ошибок, параметры вызовов, CSV, нормализация формы (Supabase подменён) | 70 тестов проходят |
| База | `npm run test:sql` | 78 проверок под ролями anon / кладовщик / руководитель: RLS, права, ограничения, статусы, выдача, возврат, продление, просрочки, отчёты | 78 из 78 |
| Слой доступа против PostgREST | `npm run test:http` | Настоящий `api/index.js` против PostgREST v12.2.3 и PostgreSQL 16: формы ответов, права, сообщения | 8 из 8 |

Тесты проверялись «на падение»: при намеренно ослабленных политиках, триггере и проверках роли они краснели (11 проверок SQL, 1 в HTTP-наборе). Тесты базы идут на PostgreSQL 16 с **заглушкой схемы `auth`** (`supabase/tests/auth_stub.sql`, `auth.uid()` повторяет определение Supabase), а не на самом Supabase.

Не покрыто тестами: одновременные запросы (блокировка `FOR UPDATE` перенесена из предыдущей версии, но гонка не воспроизводилась), вход через настоящий Supabase Auth, поведение бесплатного тарифа.

## 8. Процесс разработки с ИИ

Перенос выполнен агентом Claude Code в несколько шагов: чтение схемы, сервисов и маршрутов предыдущей версии → проект правил (`frontend/CLAUDE.md`) → SQL-миграции → тесты базы → слой доступа и интерфейс → интеграционный прогон через PostgREST → документация. Заказчик задавал решения (вход по email, отдельная папка проекта).

Что дало проверки:
- Тест на `DOMException` показал, что таймаут запроса принимался за «ошибку сервера» вместо «нет соединения» (числовой код 20 принимался за SQLSTATE) — исправлено в `client.js`.
- Проверка «до обращения к базе» выявила, что построитель запроса создавался раньше валидации формы — порядок исправлен.
- Прежние сообщения об ошибках сохранены дословно: тесты слоя доступа сверяют их с текстом из предыдущей версии.
- Тесты базы и HTTP-набор намеренно «ломались» (ослабленный RLS, убранный триггер, отключённая проверка роли), чтобы убедиться, что они способны падать.

Правила, по которым работал агент, лежат в `frontend/CLAUDE.md`.
