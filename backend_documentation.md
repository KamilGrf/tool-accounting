## 1. Архитектура и выбор решения

```
┌────────────┐  /api (прокси Vite)  ┌──────────────────────────┐   SQL ($1…)   ┌──────────────┐
│  Браузер   │ ───────────────────► │  API  (Node.js, :3001)   │ ────────────► │ PostgreSQL 16 │
│  React SPA │ ◄─────────────────── │  app → services → repos  │ ◄──────────── │  (том pgdata) │
└────────────┘  JSON + cookie       └──────────────────────────┘               └──────────────┘
                                       логи (JSON) → docker logs
```

**Слои API** (`backend/src`): `app.js` (маршруты, вход, роли, CORS, ошибки, журнал запросов) → `services.js` и `userService.js` (логика, транзакции) → `repositories.js` (запросы по таблицам) → `db.js` (пул соединений `pg`).

**Выбор: вариант B (self-hosted) — PostgreSQL в Docker и собственный API.**

| Критерий | Supabase (A) | Self-hosted (B) — выбран |
|---|---|---|
| Логика выдачи/возврата (блокировка строки, транзакции, ограничения) | Только через SQL-функции/RPC | Обычный код сервиса, переносимый и тестируемый |
| Готовая логика проекта | Нужно переписывать под RLS и Supabase Auth | Переиспользована логика из SQLite-версии (`App`) |
| Доступ в среде разработки | Нужен облачный аккаунт и проект (создаётся человеком) | Docker Desktop на локальной машине |
| Стоимость и зависимость от поставщика | Бесплатный тариф с лимитами, привязка к сервису | Свободно, любой VPS или локально |
| Минусы | — | Больше кода и ответственности за безопасность, собственный JWT, нет готовой панели |

Обоснование для данного проекта: система небольшая, бизнес-правила (конфликты выдачи, роли, CSV) удобнее держать в коде API; тестировать можно локально без облака. Ограничение выбора: **на VPS система не развёртывалась** (VPS не было); конфигурация подготовлена так, что перенос описан в разделе 3.2, но этот путь не проверен.

Права доступа реализованы **middleware в API** (вместо RLS Supabase): таблица маршрутов с явным уровнем доступа.

## 2. База данных

### 2.1. Схема

```
categories 1──* tools 1──* issues *──1 employees
                              │ issued_by, returned_by
                              ▼
                           users  (role: storekeeper | manager)
```

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `categories` | Категории инструментов | `name` уникально |
| `tools` | Инструменты | `lower(inv_number)` уникален; `price >= 0`; `status IN (in_stock, issued, repair, written_off)`; FK на категорию |
| `employees` | Получатели инструмента (не пользователи системы) | — |
| `issues` | Выдачи | `due_at >= issued_at`; `returned_at >= issued_at`; **частичный уникальный индекс** `(tool_id) WHERE returned_at IS NULL` — один инструмент не может быть выдан двум людям даже при гонке; FK |
| `users` | Пользователи | `lower(login)` уникален; `role IN (storekeeper, manager)`; `password_hash`, `failed_attempts`, `locked_until` |
| `schema_migrations` | Журнал применённых миграций | служебная |

Типы: даты — `date`, деньги — `numeric(12,2)`, метки времени — `timestamptz`. Файлы: [001_schema.sql](backend/migrations/001_schema.sql) (базовая схема, перенос с SQLite), [002_users.sql](backend/migrations/002_users.sql) (пользователи, `issued_by`, `returned_by`).

### 2.2. Миграции

`backend/src/migrate.js` применяет `migrations/*.sql` по порядку имён, каждую в транзакции, записывая имя в `schema_migrations`; повторный запуск безопасен. Миграции запускаются автоматически при старте API. Применённые файлы не редактируются: новое изменение — новый файл.

### 2.3. Проектирование схемы с ИИ

Запрос агенту: перенести схему SQLite (`App/src/db.js`) на PostgreSQL с учётом ТЗ ДЗ3 (пользователи, роли, кто выдал), без потери ограничений. Что агент предложил и что скорректировано при проверке:

| Решение | Было в SQLite | Стало и почему |
|---|---|---|
| Ключи | `INTEGER PRIMARY KEY AUTOINCREMENT` | `GENERATED ALWAYS AS IDENTITY` (современная замена `serial`) |
| Даты | `TEXT` | `date`: сравнения и вычитание дат на стороне БД (дни просрочки считает SQL) |
| Деньги | `REAL` | `numeric(12,2)`: без ошибок округления; драйвер возвращает число |
| Инв. номер | уникальный `TEXT` | уникальный индекс по `lower(inv_number)`: «инв-1» и «ИНВ-1» — один номер (проверено тестом) |
| Логин | — | уникальный индекс по `lower(login)` |
| Двойная выдача | уникальный индекс | сохранён (частичный), плюс `SELECT … FOR UPDATE` в сервисе; гонка проверена тестом |
| Кто сделал операцию | нет | `issued_by`, `returned_by` → `users` |
| Дополнительный `CHECK` | только `due_at >= issued_at` | добавлен `returned_at >= issued_at` |
| Индексы | по категории, по сотруднику | добавлены по статусу и частичный индекс просроченных открытых выдач |

Исправление после проверки: в первом варианте поиска использовался `LIKE`, который в SQLite не различает регистр только для латиницы; в PostgreSQL применён `ILIKE` с экранированием `%` и `_`. Для корректной работы с кириллицей выбран образ `postgres:16` на Debian (glibc, локаль `en_US.utf8`); тест на «дрель» / «Дрель» проходит. Образ на Alpine я не проверял.

## 3. Развёртывание

### 3.1. Локально (проверено)

Нужны Docker Desktop и Node.js 22.5+. Пошагово — в [README.md](README.md). Кратко:

```bash
cp .env.example .env            # замените все change-me
docker compose up -d --build    # БД + API: миграции и начальные данные при старте
curl http://localhost:3001/api/health
```

Состав `docker-compose.yml`:
- `db`: `postgres:16`, том `pgdata`, `healthcheck` (`pg_isready`), порт опубликован только на `127.0.0.1:5433`;
- `api`: образ из `backend/Dockerfile` (Node 22 Alpine, зависимости ставятся `npm ci --omit=dev`, запуск от пользователя `node`), стартует после `healthy` у БД, порт `127.0.0.1:3001`.

### 3.2. На VPS (подготовлено, не проверялось)

1. Установить Docker и Compose на сервер, клонировать репозиторий.
2. Создать `.env` на сервере (случайные значения; `COOKIE_SECURE=true`, `CORS_ORIGINS` — адрес frontend, `SEED_DEMO=false`).
3. Поставить перед API обратный прокси с HTTPS (Caddy или nginx): без HTTPS cookie с флагом `Secure` не работает, а пароли пойдут открытым текстом.
4. Порты БД наружу не открывать; в compose она и так привязана к `127.0.0.1`.
5. Frontend собрать (`npm run build`) и раздавать тем же прокси, чтобы запросы шли на один источник.

### 3.3. Переменные окружения

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Учётные данные БД | обязательны |
| `DB_HOST_PORT`, `API_HOST_PORT` | Порты на хосте | 5433, 3001 |
| `JWT_SECRET` | Ключ подписи сессий, **не короче 32 символов** | обязателен |
| `CORS_ORIGINS` | Разрешённые источники через запятую | пусто = любой чужой источник запрещён |
| `COOKIE_SECURE` | Флаг `Secure` у cookie (включить при HTTPS) | `false` |
| `ALLOW_REGISTRATION` | Открытая регистрация кладовщиков | `true` |
| `SEED_DEMO` | Загрузить демо-данные в пустую БД | `false` |
| `MANAGER_LOGIN`, `MANAGER_PASSWORD` | Создать руководителя при первом запуске (пароль ≥ 8 символов) | не заданы: руководителя не будет |
| `LOG_LEVEL` | `debug` / `info` / `warn` / `error` | `info` |
| `TZ` | Часовой пояс (влияет на `CURRENT_DATE`) | `Europe/Moscow` |

Секреты хранятся только в `.env` (в `.gitignore`); в репозитории — `.env.example` с `change-me`. API не стартует без `JWT_SECRET` и `DATABASE_URL`.

## 4. API

Базовый адрес: `http://localhost:3001`. Все данные — JSON; ошибки — `{"error": "<сообщение на русском>"}`. Сессия — cookie `session` (HttpOnly). Уровни доступа: **публично**, **любой вошедший**, **руководитель**.

### 4.1. Маршруты

| Метод и путь | Доступ | Назначение | Успех | Ошибки |
|---|---|---|---|---|
| `GET /api/health` | публично | Проверка API и БД | 200 | 503 |
| `POST /api/auth/register` | публично | Регистрация кладовщика `{login, password}` | 201 | 400, 403, 409 |
| `POST /api/auth/login` | публично | Вход `{login, password}` | 200 + cookie | 400, 401, 429 |
| `POST /api/auth/logout` | вошедший | Выход | 204 | 401 |
| `GET /api/auth/me` | вошедший | Текущий пользователь | 200 | 401 |
| `GET /api/categories` · `POST` · `PUT /:id` · `DELETE /:id` | вошедший | Категории | 200 / 201 / 204 | 400, 404, 409 |
| `GET /api/tools?q=&category=&status=` | вошедший | Список с поиском (регистр не важен, в том числе кириллица) | 200 | 400 |
| `GET /api/tools/:id` · `POST /api/tools` | вошедший | Карточка · создание | 200 / 201 | 400, 404, 409 |
| `PUT /api/tools/:id` | вошедший (списание — руководитель) | Изменение, смена статуса | 200 | 400, 403, 404, 409 |
| `DELETE /api/tools/:id` | **руководитель** | Удаление инструмента без истории | 204 | 403, 404, 409 |
| `GET/POST /api/employees`, `PUT/DELETE /api/employees/:id` | вошедший | Сотрудники | 200 / 201 / 204 | 400, 404, 409 |
| `GET /api/issues?active=1&overdue=1&tool=&employee=` | вошедший | Список выдач | 200 | 400 |
| `POST /api/issues` | вошедший | Выдать `{tool_id, employee_id, due_at, issued_at?}` | 201 | 400, 404, 409 |
| `POST /api/issues/:id/return` | вошедший | Принять `{condition_note?, to_repair?, returned_at?}` | 200 | 400, 404, 409 |
| `POST /api/issues/:id/extend` | вошедший | Продлить срок `{due_at}` | 200 | 400, 404, 409 |
| `GET /api/stats` | **руководитель** | Сводка | 200 | 403 |
| `GET /api/report/usage?category=` | **руководитель** | Использование инструментов | 200 | 400, 403, 404 |
| `GET /api/report/overdue.csv` | **руководитель** | CSV просрочек (BOM, «;») | 200 | 403 |

Общие ошибки любого маршрута: 401 «Требуется вход», 403 «Недостаточно прав», 404 «Ресурс не найден», 405 «Метод не поддерживается», 413 «Слишком большой запрос» (> 1 МБ), 400 «Некорректный JSON в теле запроса», 503 «Сервис временно недоступен…», 500 «Внутренняя ошибка сервера».

### 4.2. Примеры запросов

Ниже — реальные ответы запущенной системы. Пароль подставьте свой; `-c` сохраняет cookie в файл, `-b` отправляет её.

```bash
# Вход (руководитель)

     -H 'Content-Type: application/json' -d '{"login":"manager","password":"<пароль>"}'
# HTTP/1.1 200 OK
# Set-Cookie: session=<jwt>; HttpOnly; SameSite=Strict; Path=/; Max-Age=28800
# {"id":2,"login":"manager","role":"manager"}

# Поиск по-русски без учёта регистра
curl -b cj.txt 'http://localhost:3001/api/tools?q=%D0%B4%D1%80%D0%B5%D0%BB%D1%8C'
# [{"id":1,"inv_number":"ИНВ-0001","name":"Дрель ударная Bosch GSB 13 RE","category":"Электроинструмент",
#   "price":5200,"status":"issued","location":"Склад А, стеллаж 1", ...}]

# Выдача уже выданного инструмента
curl -b cj.txt -X POST http://localhost:3001/api/issues -H 'Content-Type: application/json' \
     -d '{"tool_id":1,"employee_id":2,"due_at":"2099-01-01"}'
# {"error":"Инструмент нельзя выдать: он уже выдан"}      HTTP 409

# Ошибка валидации

     -d '{"inv_number":"","name":"X","category_id":1}'
# {"error":"Поле «Инвентарный номер» обязательно для заполнения"}   HTTP 400

# Без входа
curl http://localhost:3001/api/tools
# {"error":"Требуется вход"}      HTTP 401

# Кладовщик запрашивает отчёт
curl -b keeper.txt http://localhost:3001/api/stats
# {"error":"Недостаточно прав"}   HTTP 403

# Отчёт об использовании (руководитель)
curl -b cj.txt http://localhost:3001/api/report/usage

#   "category":"Электроинструмент","issues_count":1,"days_in_use":10,"last_issued_at":"2026-10-03"}, ...]

# Чужой источник (CORS)

# {"error":"Источник запроса не разрешён"}      HTTP 403
```

## 5. Безопасность

| Область | Реализация | Проверка |
|---|---|---|
| Пароли | `scrypt` из `node:crypto`, уникальная соль, хеш `scrypt$соль$ключ`; сравнение через `timingSafeEqual` | тесты; в ответах и журнале пароля нет |
| Сессия | JWT HS256 в cookie `HttpOnly; SameSite=Strict; Path=/`, срок 8 ч; подпись проверяется в постоянное время; отвергаются подделка, истечение, `alg=none`, чужой ключ | `auth.test.js` |
| Пользователь на каждый запрос | После проверки токена пользователь читается из БД: удалённый пользователь теряет доступ сразу | код `authenticate` |
| Вход | Одинаковый ответ «Неверный логин или пароль» для неизвестного логина и неверного пароля; для неизвестного логина выполняется «пустая» проверка хеша (выравнивание времени); блокировка на 15 мин после 5 неудач → 429 **одним атомарным `UPDATE`** (параллельный перебор не обходит счётчик); для несуществующих логинов — такой же счётчик в памяти (ответ 429 не выдаёт, существует ли логин); не более 20 неудач с одного IP за 15 мин | `auth.test.js`, `hardening.test.js`, `ratelimit.test.js` |
| Роли | Явный уровень доступа у каждого маршрута (middleware в таблице маршрутов); кладовщик не видит отчёты, CSV, не удаляет инструмент и не списывает его; справочники категорий и сотрудников доступны обеим ролям, как в ТЗ ДЗ3 | `security.test.js` |
| Регистрация | По умолчанию **выключена** (`ALLOW_REGISTRATION=true` нужно задать явно); создаёт только кладовщика | `hardening.test.js` |
| Устойчивость | Некорректный адрес запроса не роняет процесс (400); необработанные исключения запроса и `unhandledRejection` логируются, процесс не завершается | `hardening.test.js` |
| SQL-инъекции | Только параметризованные запросы; динамические фрагменты `WHERE` — фиксированные строки из кода; `LIKE` экранируется | тест с «'; DROP TABLE…» |
| CORS | Список разрешённых источников из `CORS_ORIGINS`; чужой источник → 403 без заголовков CORS; `Allow-Credentials` только для разрешённых; preflight → 204 | `security.test.js` |
| CSRF | `SameSite=Strict` + запрещённые чужие источники | — |
| Секреты | Только переменные окружения; `.env` в `.gitignore` и `.dockerignore`; секреты и пароли в журнале заменяются `[redacted]` | тест на утечки в журнал |
| Заголовки | `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` для ответов API | — |
| Контейнеры | API работает от пользователя `node`; БД и API опубликованы только на `127.0.0.1` | `docker-compose.yml` |
| CSV | Значения, начинающиеся с `= + - @`, экранируются апострофом (защита от формул Excel) | тест CSV |
| Входные данные | Поля неверного типа (объект, массив, логическое значение) → 400; цена — только число или строка вида `123.45`; пароль не длиннее 128 символов | `hardening.test.js` |

Принятые риски и упрощения описаны в разделе 9.

## 6. Обработка ошибок и логирование

### 6.1. Обработка ошибок

- Ошибки валидации и конфликты — `HttpError` с кодом и русским текстом (400, 404, 409).
- Ошибки БД из-за некорректных данных (неверный формат даты, переполнение) → 400; нарушение связей → 409.
- Недоступная БД (сеть, перезапуск, таймаут подключения 3 с) → **503** «Сервис временно недоступен», причина — в журнале.
- Любая непредвиденная ошибка → 500 с общим текстом; подробности и стек — только в журнале, клиент их не получает.
- Frontend: два типа ошибок (`ApiError` / `NetworkError`), баннер с «Повторить», при 401 — переход на экран входа с сообщением «Сессия истекла», при 403 — «Недостаточно прав», форма не закрывается при ошибке.

### 6.2. Журнал

Формат — одна JSON-строка на событие в stdout: `docker compose logs -f api`.

```json
{"time":"2026-10-13T17:51:39.807Z","level":"info","msg":"api started","port":3001,"corsOrigins":["http://localhost:5173"]}
{"time":"...","level":"warn","msg":"login failed","login":"e2e.manager","ip":"172.18.0.1","known":true}
{"time":"...","level":"info","msg":"request","reqId":"3bc69a3b-…","method":"GET","path":"/api/tools","status":200,"ms":4,"userId":2}
```

Журналируются: каждый запрос (метод, путь без query, код, время, пользователь, IP, `reqId`; он же отдаётся клиенту в заголовке `X-Request-Id`), неудачные входы и блокировки, отклонённые источники CORS, ошибки БД и необработанные исключения. Уровень события зависит от кода: 2xx/3xx — `info`, 4xx — `warn`, 5xx — `error`. Пароли, токены и cookie не записываются.

### 6.3. Анализ журнала: сбой БД (разбор с ИИ)

Эксперимент: остановить БД (`docker compose stop db`) и вызвать `GET /api/health`.

| | До исправления | После исправления |
|---|---|---|
| Ответ клиенту | `500 {"error":"Внутренняя ошибка сервера"}` | `503 {"error":"Сервис временно недоступен. Попробуйте позже"}` |
| Время ответа | ≈ 5 с | ≈ 3,3 с (лимит подключения 3 с) |
| Журнал | `unhandled error … getaddrinfo EAI_AGAIN db` | `database unavailable … Connection terminated due to connection timeout` |

Вывод агента по журналу: по клиентскому ответу причину не увидеть (общий 500), но в журнале запись `unhandled error` с кодом `EAI_AGAIN` (не удалось разрешить имя `db`: контейнер остановлен), а поле `ms: 5011` показывает, что запрос ещё и висел 5 секунд. Исправления: таймаут подключения пула, обработчик ошибок пула (иначе разрыв соединения с бездействующим клиентом мог завершить процесс Node), отображение недоступности БД как 503. После возврата БД API восстановился сам, без перезапуска (проверено). Регрессионный тест: `БД недоступна: быстрый ответ 503…`.

## 9. Что не сделано и не проверено

- **Не развёрнуто на VPS и не опубликовано на GitHub.** Инструкция (раздел 3.2) не проверялась. Ссылку на репозиторий и деплой нужно создать отдельно.
- **Supabase не использовался**: выбран self-hosted вариант (раздел 1).
- **HTTPS не настроен** (локальная разработка); `COOKIE_SECURE=true` нужен вместе с прокси.
- **Отзыв выданных токенов не сделан**: выход очищает cookie в браузере, но сам токен действует до истечения (8 часов); удалённый пользователь доступ теряет сразу, так как пользователь читается из БД на каждый запрос. Нет смены пароля.
- **Ограничения входа для неизвестных логинов и по IP хранятся в памяти процесса**: после перезапуска API сбрасываются, при нескольких экземплярах API не общие. За обратным прокси нужно передавать настоящий IP клиента.
- **Блокировка менеджера** серией неверных паролей остаётся возможной (на 15 минут); смягчается лимитом по IP.
- **Открытая регистрация** (при `ALLOW_REGISTRATION=true`) даёт любому роль кладовщика; в промышленной среде отключается.
- **Приложение подключается к БД суперпользователем** (владелец БД из `POSTGRES_USER`), секреты передаются переменными окружения, а не Docker secrets. В продуктиве нужны отдельные роли БД для миграций и для работы.
- **Нет границ дат** (допускается `9999-12-31`), нет `CHECK` на длины текстовых полей на уровне БД, нет пагинации списков, нет advisory-lock для миграций при нескольких экземплярах API.
- **Нет резервного копирования БД** и мониторинга; журналы не собираются централизованно.
- **Нагрузочное тестирование не проводилось**; быстродействие измерено только отдельными запросами.
- **Frontend проверен в одном браузере** (встроенная панель), адаптив — в эмуляции.
- Тестовые учётные записи для ручной проверки (`e2e.manager`, `e2e.keeper`, `doc.keeper`) создавались в локальной БД разработки и удалены при её пересоздании (проверка развёртывания с нуля); в репозитории их нет.
