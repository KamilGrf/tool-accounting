# Анализ логов с помощью ИИ

## 1. Где лежат логи

| Источник | Что в нём | Как посмотреть |
|---|---|---|
| **Таблица `client_logs`** (Supabase) | Предупреждения и ошибки браузерного приложения: сбои API, потеря связи, необработанные ошибки, падения отрисовки. Только пользователи, вошедшие в систему | Руководитель: функция `list_client_logs`. Владелец проекта: SQL Editor, `select * from public.client_logs order by created_at desc limit 200` |
| **Журнал функции `/api/health`** (Vercel) | Одна JSON-строка на каждый вызов проверки здоровья: статус, упавшие проверки, время | Vercel → проект → Logs (поиск по тексту `health`); экспорт из панели |
| **Журналы Supabase** | Запросы к API, база данных (медленные запросы, блокировки), служба входа | Панель Supabase → Logs |
| **Консоль браузера** | Те же записи в формате JSON, в том числе неудачные входы (`auth_failed`), которые до входа в центральное хранилище не попадают | Инструменты разработчика → Console |

**Формат записи** (одна JSON-строка): `ts`, `level` (`debug`/`info`/`warn`/`error`), `message` (короткий код события, например `api_error`), `context` (технические поля: `op` — какой вызов, `status`, код ошибки), `route` (путь страницы без параметров), `release` (коммит сборки). Личные данные в журнал не попадают: адреса почты маскируются (`[email]`), поля с именами вроде `password`, `token`, `email`, `phone` скрываются, тексты режутся до 300 знаков.

## 2. Типичные записи и с чего начинать

| Запись | Что обычно значит | Первая проверка |
|---|---|---|
| `network_error` | У пользователя пропала связь или сервер не ответил за 15 с | Один пользователь или много? Есть ли в это время `health` со статусом `down`? |
| `api_error` (500) | Ошибка на стороне базы или API | Журнал Postgres в Supabase за это время; сколько пользователей затронуто |
| `api_denied` (401/403) | Истёк вход или права не позволяют операцию | Какая роль; не сменилась ли роль; что открыл пользователь (`route`) |
| `unhandled_rejection`, `uncaught_error` | Ошибка в коде приложения, которую никто не обработал | Строки стека, страница (`route`), коммит (`release`) |
| `render_crash` | Страница упала при отрисовке (сработала «граница ошибок») | `componentStack`: какой компонент, затем воспроизвести на тех же данных |
| `health` со статусом `down` | Не отвечает база или служба входа (критические проверки) | Поле `failed` показывает, какая проверка и почему (`timeout`, `http_404`...) |
| `health` со статусом `degraded` | Недоступна только проверка Google: вход через Google может не работать | Повторить через несколько минут, статус Google |

## 3. Промпты (структура Role–Task–Context–Format)

Журнал вставляется в промпт целиком (или выгружается файлом). Перед отправкой внешнему ИИ убедитесь, что в нём нет личных данных: логгер их уже маскирует, но выгрузка из Supabase и Vercel может содержать больше полей.

**Промпт 1. Разбор журнала за период**

```
Role: ты инженер поддержки, который разбирает журнал веб-приложения.
Task: найди в журнале проблемы, сгруппируй записи по причине, оцени серьёзность и скажи, что проверить первым делом.
Context: приложение «Учёт инструментов» (React + Supabase, хостинг Vercel). Поля записи: level, message (код события),
context.op (какой вызов), context.status, route (страница), user_id (обезличенный номер), source (browser или vercel).
Записи `health` пишет сервер: status ok/degraded/down, failed — упавшие проверки. Журнал: <вставить>.
Format: таблица «группа проблем | записи (время, сколько) | серьёзность (высокая/средняя/низкая) | вероятная причина | что проверить».
Отдельно перечисли, что установлено по журналу, а что только гипотеза.
```

**Промпт 2. Корреляция по времени**

```
Role: ты инженер надёжности (SRE).
Task: построй хронологию событий и найди совпадения серверных и клиентских записей по времени.
Context: те же данные; записи source=vercel — проверки здоровья каждые 15 минут и по запросу; source=browser — ошибки пользователей.
Format: хронология (время — событие), затем список «совпадения и что они могут значить», затем «чего не хватает в журнале, чтобы быть уверенным».
```

**Промпт 3. Корневая причина одной ошибки**

```
Role: ты разработчик React, который ищет причину ошибки.
Task: по записи и стеку объясни вероятную причину и предложи минимальное исправление и тест.
Context: запись журнала: <вставить одну запись с context.stack>. Исходный файл компонента: <вставить>.
Format: причина (1–2 предложения), исправление (код), тест (код), риск исправления.
```

## 4. Проверка на типичных ошибках

Пример журнала [`sample-logs.jsonl`](sample-logs.jsonl) сгенерирован **настоящим логгером приложения** по сценарию с типичными сбоями (записи `browser`) плюс строки в формате функции `/api/health` (записи `vercel`). Это **синтетические данные**, а не реальный журнал сайта; поле `release` в них `dev`, потому что генерация шла в тестовом окружении (в работающем приложении там стоит коммит). Адрес почты в записи о падении отрисовки замаскирован самим логгером.

Промпт 1 и промпт 2 применены к этому журналу (разбор выполнил ИИ — Claude в этой сессии). Результат:

| Группа | Записи | Серьёзность | Вероятная причина (гипотеза) | Что проверить |
|---|---|---|---|---|
| **Сбой базы данных** | `health` down (`database:timeout`) 10:06:58 и 10:07:40; три `api_error` 500 на `rpc/issue_tool` 10:07:12–10:07:58 у двух пользователей; `health` снова ok в 10:08:41, но с задержкой 654 мс при обычных ~200 | Высокая | Кратковременная перегрузка или блокировка в базе: окно сбоя совпадает с ошибками именно операции выдачи (она блокирует строку инструмента) | Журнал Postgres в Supabase за 10:06–10:09: медленные запросы, блокировки, лимит соединений; не засыпал ли бесплатный проект |
| **Падение скрипта** | `unhandled_rejection`: `Cannot read properties of undefined (reading 'map')`, страница `/issues`, 10:15:44, пользователь u-9d01 | Средняя | Код ожидал массив, а получил `undefined`, вероятно после неудачной загрузки списка (у этого же пользователя в 10:07:31 была ошибка 500) | Стек указывает на `IssuesPage`: проверить обработку пустого или ошибочного ответа, добавить защиту и тест |
| **Падение отрисовки** | `render_crash` в `ToolDetail`, страница `/tools`, 10:18:05, пользователь u-7f3a | Средняя | По журналу неясно: компонент указан, причины в записи нет. Тот же пользователь в 10:03–10:04 терял связь, возможна связь с частично загруженными данными | Воспроизвести карточку инструмента на неполных данных |
| **Отказ в доступе** | `api_denied` 403 на `rpc/report_stats` и `rpc/report_usage`, страница `/report`, 10:12:20–21, пользователь u-12bc | Низкая / средняя | Эти вызовы делает только страница отчёта, но кладовщику она не показывается. Либо роль пользователя изменилась (понижен руководитель), либо устарел вход, либо вызов сделан напрямую | Проверить роль u-12bc в `profiles`; убедиться, что сервер отказал правильно (так и вышло: 403) |
| **Потеря связи у одного пользователя** | 5 × `network_error` на `rpc/list_tools`, 10:03:02–10:04:33, один пользователь u-7f3a | Низкая | Проблема на стороне клиента (сеть): сервер в это время отвечал, ошибок 5xx не было | Повторится ли у других пользователей; действий не требуется |
| **Сервис Google** | `health` degraded (`google:http_503`) 10:30:02 | Низкая | Сервис Google временно недоступен: страдает только вход через Google | Повторить проверку позже |

**Что установлено по журналу:** окно сбоя базы (две записи `down` и три ошибки 500 в одни и те же две минуты) и то, что отказы в доступе и потеря связи у одного пользователя по времени со сбоем базы не совпадают. **Что остаётся гипотезой:** причина сбоя базы, причина падения отрисовки и причина отказа в доступе: в журнале нет данных, чтобы это подтвердить.

**Чего не хватает журналу для большей уверенности:** кода ошибки базы в `api_error` (сейчас записывается только статус), состояния данных в момент падения отрисовки и роли пользователя в записи `api_denied`.

## 5. Ограничения

- В центральное хранилище попадают только записи вошедших пользователей (база отказывает анонимным): ошибки до входа видны лишь в консоли браузера.
- От одного пользователя принимается не больше 30 записей в минуту, а из одной страницы уходит не больше 20 записей за просмотр: при лавине ошибок часть записей теряется (в консоли остаются все).
- Записи хранятся, пока их не удалят: функция `purge_client_logs(дни)` (только руководитель) удаляет старые; автоматического расписания нет.
- Выводы ИИ по журналу — гипотезы: причины подтверждаются журналами Supabase и кодом.
