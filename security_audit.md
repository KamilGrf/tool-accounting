# Аудит безопасности — АС «Учёт инструментов»

Дата аудита: 16–18 октября 2026. Объект: ветка `security-audit` репозитория `tool-accounting` (React-интерфейс, Supabase: Auth, PostgreSQL с RLS и функциями, функция Vercel `/api/health`, GitHub Actions). Классификация — по OWASP Top 10 (2021).

## 1. Итог

Найдено **14 проблем**: 1 критическая, 1 высокая, 9 средних, 3 низких. Все исправлены в коде. Отдельно описаны остаточные риски, которые зависят от настроек панелей Supabase и Google и не меняются из кода (раздел 5): для них даны точные шаги владельцу проекта.

Главное: до аудита любой человек мог зарегистрироваться и сразу получить права кладовщика (чтение сотрудников, выдача инструментов). Теперь новый аккаунт получает роль `pending` и не видит данных, пока руководитель не подтвердит его.

Статус проверки: все исправления покрыты автотестами (194 теста интерфейса, 147 проверок SQL под ролями anon / ожидающий / кладовщик / руководитель, 11 проверок слоя доступа против PostgREST) и проходят в CI. Миграции 007 и 008 применены только в тестовой базе CI; **в боевом Supabase их ещё нужно выполнить** (раздел 6). Атаки на работающий сайт я не проводил.

## 5. Остаточные риски и рекомендации

| Риск | Почему остаётся | Что сделать |
|---|---|---|
| Руководитель обладает полной властью: может выдать роль любому и списать инструмент | Так задумано ролевой моделью; каждое изменение роли теперь записывается в `audit_log` | Выдавать роль руководителя минимальному кругу; периодически смотреть `list_audit_log` |
| Адрес почты при регистрации может быть чужим, если в Supabase выключено «Confirm email» | Это настройка панели, из кода её не переключить | Supabase → Authentication → Providers → Email: включить **Confirm email**; до этого подтверждать только знакомых (страница помечает неподтверждённые) |
| Слабые пароли и перебор | Длина пароля и лимиты запросов входа — настройки Supabase | Authentication → Policies: длина не меньше 10–12; оставить лимиты по умолчанию; проверить, что включена защита CAPTCHA при необходимости |
| Доверие к скриптам Google (Analytics грузится с `googletagmanager.com`) | Загружается только после согласия посетителя; при компрометации Google скрипт получит доступ к странице | При необходимости отказаться от аналитики (переменная `VITE_GA_MEASUREMENT_ID` пустая — она отключена полностью) |
| Хранилище Supabase (Storage API) включено, но не используется | Закрыть можно только в панели | Оставить без бакетов; публичных бакетов не создавать |
| `/api/health` публичный и раскрывает названия проверок, время и 7 знаков коммита | Нужен внешнему монитору | Секретов в ответе нет; при желании закрыть токеном в заголовке |
| Одновременные изменения ролей проверены рассуждением | Автоматический тест двух параллельных сессий не писался | Можно добавить тест с двумя соединениями psql |

## 6. Что нужно сделать владельцу проекта

1. В Supabase → SQL Editor выполнить по очереди `supabase/migrations/20261018000007_access_approval.sql` и `20261018000008_audit_hardening.sql`.
2. Убедиться, что в боевой базе есть хотя бы один руководитель (иначе подтверждать новые аккаунты будет некому): существующие роли миграция не меняет, но новые регистрации получают `pending`. Если руководителя нет, назначить его SQL-командой `update public.profiles set role = 'manager' where email = '…'`.
3. Выполнить настройки раздела 5 (Confirm email, длина пароля).
4. После выполнения миграций сообщить мне: тогда можно вливать ветку в `main` (деплой проверит `/api/health`).

## 7. Как повторить проверки

Все проверки выполняются в CI при каждом пуше (GitHub Actions: задания «Frontend» и «Database»). Локально для интерфейса: `npm test`, `npm run lint`, `npm audit --omit=dev` в папке `frontend`.
