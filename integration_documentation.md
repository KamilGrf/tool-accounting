## 1. CI/CD

### 1.1. Платформа и запуск

GitHub Actions, файл `.github/workflows/ci.yml`. Запускается при каждом пуше в любую ветку, при pull request и вручную. Два независимых задания:

| Задание | Шаги |
|---|---|
| **Frontend** | `npm ci` → ESLint → проверка Prettier → тесты (Vitest) → `npm audit` для рабочих зависимостей (падает при серьёзности high) → сборка |
| **Database** | SQL-тесты на PostgreSQL 16 (миграции, RLS, функции) → слой доступа приложения против PostgREST |

Пример конфигурации (фрагмент):

```yaml
on:
  push:
    branches: ['**']
  pull_request:
  workflow_dispatch:
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
permissions:
  contents: read
jobs:
  frontend:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: frontend } }
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 24, cache: npm, cache-dependency-path: frontend/package-lock.json }
      - run: npm ci
      - run: npm run lint
      - run: npm run format:check
      - run: npm test
      - run: npm audit --omit=dev --audit-level=high
      - run: npm run build
```

### 1.2. Проверки качества кода

- **ESLint 9** (`frontend/eslint.config.js`): рекомендованные правила, правила React и хуков; запуск с `--max-warnings 0`, то есть предупреждение тоже ломает сборку. Версия 9, а не 10: плагин `eslint-plugin-react` пока не поддерживает 10.
- **Prettier 3** (`frontend/.prettierrc.json`): 4 пробела, одинарные кавычки, точки с запятой, 140 колонок, `LF`.
- Переводы строк приведены к `LF` и закреплены в `.gitattributes`: CI работает на Linux.
- Линтер при первом запуске нашёл настоящую проблему: невидимый символ BOM в исходниках (`csv.js` и тесты). Исправлено, теперь он собирается через `String.fromCharCode(0xfeff)`.

### 1.3. Деплой

Автоматический деплой при пуше в `main` выполняет интеграция Vercel с GitHub (по инструкции из README проект Vercel подключён к репозиторию с Root Directory `frontend`; настройки самого проекта Vercel в репозитории не хранятся). В пайплайне GitHub Actions шага деплоя нет: он служит барьером качества, который должен быть зелёным до влития в `main`. Переменные окружения для сборки (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_GA_MEASUREMENT_ID`) заданы в настройках Vercel, не в репозитории.

### 1.4. Как проверено

- Ветка `ci-setup`: оба задания зелёные (все шаги).
- Тестовая ветка с намеренно сломанным файлом: задание Frontend упало на шаге Lint (остальные шаги пропущены), Database осталось зелёным. После проверки ветка удалена.
- Локально те же команды (`lint`, `format:check`, `test`, `build`, `audit`) проходят.

### 1.5. Ограничения

- Шаг «проверить, что выкатилось» (опрос работающего сайта после деплоя) пока не добавлен.
- Деплой не зависит от результата CI: Vercel выкатывает `main` независимо. Чтобы блокировать деплой при красном CI, нужно отключить автодеплой Vercel и деплоить из пайплайна с токеном.
- Скачивание образов Docker Hub на серверах GitHub подпадает под лимиты Docker Hub; при превышении задание Database может упасть без вины кода.

## 2. OAuth2: вход через Google

### 2.1. Как это работает

Вход выполняет Supabase Auth (Google OAuth 2.0, схема Authorization Code с PKCE); собственного бэкенда в проекте нет, поэтому «серверную часть потока» (обмен кода на токен, хранение секрета) берёт на себя Supabase.

```
Браузер ──(кнопка)──► Supabase /authorize ──► Google (согласие)
   ▲                                              │
   └── сайт с ?code=… ◄── Supabase /callback ◄────┘   код обменивается на сессию в браузере (PKCE)
```

1. Кнопка «Войти через Google» (`LoginPage`) вызывает `supabase.auth.signInWithOAuth({ provider: 'google', redirectTo: <адрес сайта> })`.
2. После согласия Google возвращает пользователя в Supabase, а тот на сайт с одноразовым кодом; клиент обменивает код на сессию (`flowType: 'pkce'`): токены не попадают в адресную строку и историю.
3. Триггер базы данных создаёт профиль с ролью `storekeeper`: роль берётся не из Google и не из запроса. Руководителем делает SQL-команда (см. README).
4. Кнопка показывается только если провайдер включён в проекте (приложение читает публичные настройки `/auth/v1/settings`); иначе нажатие вело бы на страницу ошибки.

### 2.2. Настройка (выполняет владелец проекта)

> Названия пунктов в консолях Google и Supabase приведены по памяти и могут отличаться: интерфейсы менялись.

**Google Cloud Console** (console.cloud.google.com):
1. Создайте проект (например, `tool-accounting`).
2. Экран согласия OAuth (раздел APIs & Services → OAuth consent screen, в новом интерфейсе Google Auth Platform): тип **External**, название приложения, email поддержки, email разработчика. Области доступа оставьте по умолчанию (`openid`, `email`, `profile`): они не считаются чувствительными.
3. Режим публикации (раздел **Audience**). В режиме **Testing** войти могут только перечисленные тестовые пользователи (до 100): добавьте себя и проверяющего (**Add users**). Чтобы вход был открыт всем, нажмите **Publish app** (**In production**). Кнопка неактивна, пока в разделе **Branding** не заполнены: название приложения, email поддержки, адрес главной страницы `https://tool-accounting.vercel.app/` и адрес политики конфиденциальности `https://tool-accounting.vercel.app/privacy` (страница есть в приложении и открывается без входа; код — `frontend/src/pages/PrivacyPage.jsx`). Если Google попросит указать авторизованный домен, укажите `tool-accounting.vercel.app`. Для базовых областей (`openid`, `email`, `profile`) проверка Google, насколько я знаю, не требуется, но приложение может отображаться как непроверенное.
4. Credentials → Create credentials → **OAuth client ID** → Web application:
   - Authorized JavaScript origins: `https://tool-accounting.vercel.app` и `http://localhost:5173`
   - Authorized redirect URIs: `https://<project-ref>.supabase.co/auth/v1/callback` (точный адрес показан в Supabase на странице провайдера Google)
5. Сохраните **Client ID** и **Client Secret**.

**Supabase** (панель проекта):
1. Authentication → Sign In / Providers → **Google**: включите, вставьте Client ID и Client Secret. Секрет хранится только здесь, в репозиторий и в приложение он не попадает.
2. Authentication → URL Configuration: **Site URL** `https://tool-accounting.vercel.app`; в **Redirect URLs** добавьте `https://tool-accounting.vercel.app/**` и `http://localhost:5173/**`. Без этого после входа Supabase отправит пользователя на Site URL или откажет.

Приложение настраивать не нужно: кнопка появится сама, как только провайдер включён.

### 2.3. Обработка ошибок

| Ситуация | Что видит пользователь |
|---|---|
| Закрыл окно Google или отказал | «Вход через Google отменён» (один раз, адресная строка очищается) |
| Ошибка сервера при входе | «Не удалось войти через Google. Попробуйте позже» |
| Неизвестная ошибка в адресе | «Не удалось войти через Google (код: …)»: показывается только очищенный код (латиница, цифры, подчёркивание, до 40 знаков), описание из адреса не показывается: ссылку может составить кто угодно |
| Провайдер выключен в проекте | Кнопки нет |
| Не удалось начать переход | Красное сообщение под кнопкой |
| Страница Google `redirect_uri_mismatch` | Адрес возврата в Google Cloud не совпадает с адресом из Supabase (раздел 2.2, п. 4) |

### 2.4. Безопасность

- Client Secret только в Supabase; в браузере его нет.
- PKCE; адреса возврата ограничены списком Redirect URLs.
- Роль новому пользователю назначает база данных, клиент и Google на неё не влияют.
- Если пользователь уже регистрировался по email с тем же адресом, Supabase, насколько я знаю, по умолчанию связывает входы одного подтверждённого адреса в один аккаунт; поведение зависит от настроек проекта и не проверялось.

### 2.5. Как проверено

- Автотесты (108 тестов интерфейса и слоя доступа): запуск перехода с правильными параметрами и возвратом на сайт; сообщения об ошибке возврата, чтение из строки запроса и фрагмента, очистка адреса, защита от «подделанной» ссылки; кнопка скрыта при выключенном провайдере; событие аналитики о входе через Google при возврате с сессией.
- В браузере на проекте Supabase проверено, что при выключенном провайдере кнопки нет.
- **Не проверено:** сам вход через Google на настоящем аккаунте (провайдер в проекте на момент написания выключен: `external.google = false`), экран согласия Google, связывание аккаунтов.

## 3. Аналитика: Google Analytics 4

### 3.1. Что и как отправляется

Модуль `frontend/src/analytics.js`, без дополнительных пакетов. Если не задан `VITE_GA_MEASUREMENT_ID` (формат `G-XXXXXXXXXX`), аналитика выключена полностью: ничего не загружается и не отправляется.

- **Согласие.** Пока посетитель не нажал «Разрешить» в баннере, тег Google не загружается и события не уходят. Ответ хранится в `localStorage`; при отказе включается документированный переключатель `ga-disable-<ID>`. Передумать можно ссылкой «Отключить / Включить аналитику» в боковом меню. Если хранилище браузера заблокировано, ответ считается «не спрашивали» и ничего не отправляется.
- **Просмотры страниц.** Автоматическая отправка отключена (`send_page_view: false`); приложение само отправляет `page_view` при каждой смене маршрута (`PageTracker`), потому что у одностраничного приложения нет настоящих перезагрузок.
- **События** (без email, имён и описаний инструментов):

| Событие | Когда | Параметры |
|---|---|---|
| `page_view` | смена маршрута | `page_path`, `page_title` |
| `login` | вход | `method`: `email` или `google` |
| `sign_up` | регистрация по email | `method: email` |
| `tool_created` | добавлен инструмент | — |
| `tool_issued` | выдан инструмент | — |
| `tool_returned` | принят возврат | `to_repair` (в ремонт или нет) |
| `issue_extended` | продлён срок | — |
| `tool_written_off` | списание | — |
| `report_exported` | выгружен CSV просрочек | — |

### 3.2. Настройка (выполняет владелец проекта)

1. В Google Analytics (analytics.google.com) создайте аккаунт и ресурс (property), затем **поток данных «Веб»** с адресом `https://tool-accounting.vercel.app`. Скопируйте **Measurement ID** (`G-…`).
2. Vercel → проект → Settings → Environment Variables: добавьте `VITE_GA_MEASUREMENT_ID` (Production) и пересоберите проект (значение зашивается при сборке: без нового деплоя оно не подействует). Для локального запуска добавьте то же значение в `frontend/.env`.
3. Проверка: откройте сайт, нажмите «Разрешить» и выполните несколько действий; в отчёте **Realtime** (Отчёты → В реальном времени) появятся активный пользователь и события.

### 3.3. Приватность и ограничения

- Данные обезличены на уровне приложения (нет email, имён, текстов). Остальное определяется Google (в GA4 IP-адреса, насколько я знаю, не сохраняются).
- Для реальной эксплуатации потребуются политика конфиденциальности и учёт требований к трансграничной передаче данных; для учебного проекта предусмотрено только согласие и возможность отказа.
- Блокировщики рекламы и режимы приватности браузеров могут блокировать Google Analytics: статистика будет заниженной.

### 3.4. Как проверено

- Автотесты (модуль): без идентификатора, с неверным форматом, без согласия и при заблокированном хранилище ничего не загружается и не отправляется; после согласия тег загружается один раз, события и просмотры попадают в очередь; после отказа отправка прекращается. Компоненты: баннер, кнопка смены ответа, отправка `page_view` при смене маршрута. События входа не содержат email (проверено тестом).
- В браузере с **тестовым** идентификатором: до согласия показан баннер и ничего не загружено; после «Разрешить» добавлен тег Google и в очередь попали `config` (без автоматического просмотра) и `page_view` с путём страницы.
- **Не проверено:** доставка данных в Google и отображение в отчётах (нужен настоящий идентификатор).
